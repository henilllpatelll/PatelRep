## Summary

This milestone's 7 phases are individually well-verified — Phase 6 alone passed intra-phase verification (20/20 must-haves), conversational UAT (0 issues), and a security audit (21/21 threats closed). But this cross-phase audit — checking phase boundaries an intra-phase audit cannot see — found **one real, previously-undetected, untested integration gap**: the AI Copilot's guest-request creation path silently bypasses the entire SLA/escalation/audit contract that Phase 5's guest-recovery system depends on. A front-desk/GM user creating a guest request via the AI Copilot chat gets a request that will never assign a fulfillment task, never SLA-escalate, and leaves no audit trail — with no error surfaced anywhere. This directly undermines the guest-recovery value proposition Phase 5 shipped, specifically for AI-created requests.

This is why the audit's overall status is `gaps_found` rather than `passed`, despite every individual phase's own verification passing cleanly. It's exactly the class of defect that only surfaces when checking across phase boundaries.

## Blocker — Must Fix Before Milestone Close

### AI Copilot guest-request fast-path bypasses Phase 5's guest-recovery contract

**File:** `apps/api/routers/ai_copilot.py:571-589` (`confirm_guest_requests`)

**What's broken:** The canonical `apps/api/routers/guest_requests.py::create_guest_request` (lines 87-166) validates category/priority, resolves `sla_minutes` from tenant SLA policies, sets `due_at`, auto-creates a linked `tasks` row (the row the escalation cron actually watches), back-fills `guest_requests.task_id`, and records a `guest_request_events` audit row. `confirm_guest_requests` does a bare `insert()` with only `tenant_id`/`title`/`description`/`room_id`/`guest_name`/`status`/`created_by` — none of the above. `GuestRequestPreview` and its upstream parser never even capture `category`/`priority`/`guest_impact`, so there's no data to forward even if the handler wanted to.

**Impact:** Any guest request created via the AI Copilot chat interface is invisible to `internal.py::check_escalations` (scans only `tasks`), never SLA-escalates, and leaves no audit trail — with zero error surfaced to the user, front desk, or GM. This silently degrades the guest-recovery promise Phase 5 shipped, specifically for AI-created requests. No test exists that would catch this (existing coverage only checks auth/role requirements on the endpoint).

**Why this is a milestone-level gap, not just a Phase 6 footnote:** `guest_request_creation` was explicitly listed in Phase 6's own audit scope (06-CONTEXT.md D-01), so this should have been caught by 06-01 or 06-03's audits — it wasn't, because both plans focused on RBAC/tenant-isolation/credit-accounting for the endpoints without tracing this specific handler's data completeness against Phase 5's contract. This is precisely the kind of cross-phase gap an intra-phase audit structurally cannot see.

**Fix direction:** `confirm_guest_requests` should call into (or replicate) `create_guest_request`'s full contract: capture category/priority/guest_impact in `GuestRequestPreview` and the parser schema, resolve `sla_minutes`, set `due_at`, auto-create the linked task, and record the audit event — matching the pattern `confirm_tasks`/`confirm_work_orders` already correctly follow in the same file.
