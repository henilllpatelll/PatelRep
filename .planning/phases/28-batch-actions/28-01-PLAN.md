<objective>
Add two batch endpoints for room-readiness predictions — `POST /v1/housekeeping/room-readiness/batch-reassign` and `POST /v1/housekeeping/room-readiness/batch-acknowledge` — each a thin loop over Phase 27's existing single-item coroutine (`reassign_at_risk_room` / `acknowledge_at_risk_room`), with a per-item best-effort result list.

Purpose: AI-09 and AI-10 — let a supervisor/GM commit a reassign or acknowledge across multiple HIGH-risk rooms in one call while still getting a per-room outcome (e.g. "3 reassigned, 1 escalated: no capacity"), not a single aggregate pass/fail.
Output: One new request model, two new endpoints, one new test file. No new schema, no new cron, no new business-logic path.
</objective>

  <action>
In `apps/api/models/requests.py`, add ONE new model (both room-readiness batch endpoints take the same shape — a list of room ids):
```python
class BatchRoomReadinessRequest(SanitizedBaseModel):
    room_ids: List[UUID4] = Field(min_length=1, max_length=50)
```
Place it near `BulkArchiveWorkOrdersRequest` (requests.py:786). Cap is 50 per CONTEXT.md (HIGH-risk lists at a 50-150 room property are inherently small; this is a synchronous request, not a background sweep). Do NOT reuse the 200 cap.

In `apps/api/routers/housekeeping.py`, add two endpoints, both gated `require_role("gm", "housekeeping_supervisor")` (mirror the existing single-item gate at housekeeping.py:1274 exactly — do NOT widen it):

1. `POST /housekeeping/room-readiness/batch-reassign` -> `batch_reassign_rooms(body: BatchRoomReadinessRequest, current_user=Depends(require_role("gm","housekeeping_supervisor")))`
2. `POST /housekeeping/room-readiness/batch-acknowledge` -> `batch_acknowledge_rooms(...)`

Each handler MUST:
- Loop `body.room_ids` and call the corresponding existing single-item coroutine per id — `await reassign_at_risk_room(room_id=str(rid), current_user=current_user)` / `await acknowledge_at_risk_room(...)`. This is the established in-file pattern (reassign_at_risk_room already calls `create_assignments` directly, housekeeping.py:1318). Do NOT reimplement the guard/validation/scoring logic and do NOT add a bulk `.in_()` pre-fetch of room state — the per-item live re-read (PITFALL #1: no stale-snapshot batch writes) and per-item 404-on-missing/wrong-tenant (via `_fetch_room_prediction_or_404` / `_ensure_tenant_row` inside the coroutine) must both be inherited from the looped coroutine, not shortcut.
- Wrap EACH per-id call in its own `try/except HTTPException as e`, so one item's 409 (room no longer awaiting cleaning) or 404 (missing/cross-tenant room) becomes a per-item error entry `{"room_id": rid, "action": "error", "status": e.status_code, "detail": e.detail}` and the loop continues (PITFALL #2: best-effort, NOT all-or-nothing — do NOT copy `_bulk_archive`'s single-404-aborts-everything shape at work_orders.py:568).
- Build a results list preserving the successful coroutine's own return shape, prefixed with the room_id: reassign yields `{"room_id":..., "action":"reassigned", "housekeeper_id":...}` or `{"room_id":..., "action":"escalated", "reason":"no_eligible_housekeeper"}`; acknowledge yields `{"room_id":..., "action":"acknowledged"}` or `{"room_id":..., "action":"already_acknowledged"}`.
- Return `{"data": {"results": [...], "succeeded": <count of non-error entries>, "failed": <count of error entries>}}`, one entry per requested id, order preserved.

Add both routes to the router with a docstring; no `main.py` change needed (router already mounted). Regenerate the RBAC matrix if the drift-guard test fails (`python apps/api/scripts/generate_rbac_matrix.py`) — Phase 27-02 hit this same CI drift guard when adding routes.

  <done>Both endpoints exist, gated gm/housekeeping_supervisor, each loops its single-item coroutine with per-item try/except and returns a per-item results list wrapped in `{"data":{"results","succeeded","failed"}}`. Cap 50, min 1 enforced by the model.</done>
