<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| staff browser → `/lost-found` | Role-gated controls over disposal of a guest's physical property |
| browser → `POST /lost-found/{id}/custody-events` | The authoritative boundary; the UI gate is defence in depth only |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-08-01 | Elevation of Privilege | A housekeeper or engineer disposing of a guest's property | mitigate | `canApproveDisposition` hides the control for roles outside `{gm, housekeeping_supervisor, front_desk}`; the API returns 403 for the same set regardless of what the client sends (D-12, proven by `test_disposition_rbac_rejects_engineer_with_403` in plan 05-04) |
| T-05-08-02 | Tampering | Automated or bulk disposal bypassing human authorisation | mitigate | No bulk action, timer, or effect-driven disposal exists in this page — enforced by an explicit negative acceptance criterion. Each approval is a single confirmed action producing one append-only custody event (D-11) |
| T-05-08-03 | Repudiation | Disputed disposal with no record of who authorised it | mitigate | The API sets `disposition_approved_by` from the JWT and writes an immutable `lost_found_custody_events` row; the new custody-history disclosure makes that record readable in the UI |
| T-05-08-04 | Tampering | Misrepresenting a still-unclaimed item as disposed | mitigate | The `disposition_due` flag is rendered as a separate derived `Pill` and is deliberately kept out of `STATUS_TONE`/`STATUS_LABELS`, so an item past retention still reads as `Unclaimed` until a human acts |
| T-05-08-05 | Information Disclosure | Cross-tenant item or custody event display | mitigate | Every read goes through `lostFoundApi`, whose endpoints are already `.eq("tenant_id", current_user.hotel_id)` scoped; the client sends no tenant identifier of its own |
| T-05-08-06 | Information Disclosure | Claimant identity data (recipient name, verification method) shown broadly | accept | Visible only to authenticated staff on an authenticated route; the same data is already exposed by the existing release flow and is operationally required for custody reconstruction |
</threat_model>
