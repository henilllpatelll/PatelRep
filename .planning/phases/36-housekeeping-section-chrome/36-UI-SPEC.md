# Phase 36 — UI Design Contract

> Visual and interaction contract for `apps/web/app/(dashboard)/housekeeping/page.tsx` and its two
> non-frozen chrome components (`AssignmentSidebar.tsx`, `PredictionPanel.tsx`). `RoomStatusBoard`,
> `RoomDetailDrawer`, and `RoomCard` are content-hash-frozen (`apps/web/frozen-files.json`) and
> receive ZERO visual or behavioral changes this phase — this contract governs only the chrome
> around them. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Spacing Scale

Declared values (Tailwind default 4px-multiple scale, already project-wide):

| Token | Value | Usage in this phase |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps (`gap-1`/`gap-1.5`), pill internal padding |
| sm | 8px | Chip/pill row gaps, `AssignmentSidebar` stat-tile internal padding |
| md | 16px | `Card`/`PageHeader` internal padding, section-to-section vertical rhythm (`space-y-4`) |
| lg | 24px | — not used in this phase's chrome (single-column, compact layouts) |
| xl | 32px | — not used |
| 2xl | 48px | — not used |
| 3xl | 64px | `HousekeeperMyRoomsView` empty-state vertical padding (`py-12`/`py-20` region — convert bespoke `py-20` to `EmptyState`'s built-in `py-12`, see Copywriting Contract) |

Exceptions:
- **44px minimum touch target** on `button`/`[role=button]`/`input`/`select` at `max-width: 640px` or `(pointer: coarse)` is a global rule already in `globals.css` (lines 184-187) — applies automatically to every action in `HousekeeperRoomItem` (Start/Done/Undo), the `HousekeeperBar` chip buttons, and the assignment-mode toggle. No phase-specific override needed; do not shrink these below the global floor on mobile-width viewports even though the housekeeper view is web-unreachable in production today (defense-in-depth, per CONTEXT.md).
- `AssignmentSidebar` stat tiles and `PredictionPanel` header band use `px-3 py-2`/`px-4 py-3.5` (12px/16px-ish component-internal padding) — already-established pattern, not a new exception.

## Typography

This project does not use a single generic 4-role scale; each component declares specific pixel sizes already in production. This phase introduces no new sizes or weights — it documents the roles this phase's chrome actually renders, using only sizes/weights already present in `housekeeping/page.tsx`, `AssignmentSidebar.tsx`, and `PredictionPanel.tsx`.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 13px (`text-[13px]`) | regular (400) | 1.5 |
| Label / meta | 12px (`text-xs`) / 11px (`text-[11px]`) | medium (500) | 1.4 |
| Heading (card/section title, e.g. `AssignmentSidebar` `<h3>`, `StateBlock` error message) | 14px (`text-sm`/`text-[14px]`) | semibold (600) | 1.3 |
| Display (`PageHeader` `<h1>`, my-rooms todo/in-progress/done stat numerals) | 34px (`PageHeader`) / 18-20px (`font-display` stat numerals, existing `strong` tags at `text-sm`→numerals rendered at parent `text-sm` with `font-display`) | regular (400, per `font-display` italic/serif treatment — never bolded) | 1.1 (PageHeader) / 1.2 (stat numerals) |

Weight discipline: **regular (400) + semibold (600)** are the two structural weights for this phase's new/converted UI (StateBlock message, EmptyState title, Skeleton-adjacent labels). `font-medium` (500) continues to appear only in already-established micro-label contexts (pills, chip bar, `assignBar` copy) — an existing codebase-wide convention carried forward unchanged from Phase 30, not a new third weight introduced by this phase.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--paper` `#f7f4ee` / `--surface` `#ffffff` | Page canvas, `Card` backgrounds (my-rooms list items, `AssignmentSidebar`, `PredictionPanel` body rows) |
| Secondary (30%) | `--surface-2` `#fbf9f4` / `--surface-3` `#f1ede4` / `--line` `#e6dfd1` | `AssignmentSidebar` stat tiles, `PredictionPanel` batch-action band, `StateBlock`/`Skeleton` surfaces, borders between rows |
| Accent (10%) | `--brand`/`--accent` `#b8431c` (terracotta) | **Reserved exclusively for:** the primary "Save {n}" button in `HousekeeperBar`, the active/selected housekeeper chip's assigned-count treatment context, the `Start`/`Done` primary action buttons on `HousekeeperRoomItem` (these render `--ready` green per existing convention — accent itself is reserved for the assign-mode "Save" CTA and any link text, e.g. the `Add staff` link in the empty-staff state), VIP `Pill`, active `PageHeader` tab underline (not used this phase — no tabs) |
| Destructive / alert | `--alert` `#a6263c` | **Reserved exclusively for:** the "Confirm undo" button background, DIRTY/OCCUPIED status pills, the HIGH-risk `Pill` in `PredictionPanel`, `StateBlock`'s error icon circle (`--alert-soft` bg + `--alert` icon) — never used for anything but genuinely destructive/alert-severity states |

Additional semantic tokens already in active use and unchanged by this phase (documented, not introduced): `--ready` (teal, INSPECTED status + Done/Start buttons), `--caution` (amber, PICKUP status + MEDIUM risk), `--progress` (violet, IN_PROGRESS status), `--info` (blue, CLEAN status), `--blocked` (gray, OOO status), `--ai` (violet-indigo, `PredictionPanel`'s `AILabel`/header band — this is AI-attributed content per project convention, must keep the `AILabel` treatment).

Accent reserved for: primary Save CTA in assign mode, VIP pill, inline text links (e.g. "Add staff") — never applied to status pills, semantic room-state colors, or the AI-attribution band (those keep their own semantic/`--ai` tokens).

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA (supervisor/board view, assign mode) | "Save {{count}}" — existing `housekeeping.page.assignBar.save` + pending-count badge, unchanged |
| Primary CTA (housekeeper my-rooms view, per room) | "Start" → "Done" (two-step, existing `housekeeping.page.roomItem.start`/`done`/`confirmDone`) — unchanged, visuals only |
| Empty state heading (my-rooms) | "No rooms assigned to you today." — existing `housekeeping.page.myRooms.emptyTitle`, migrate into shared `EmptyState`'s `title` prop verbatim |
| Empty state body (my-rooms) | "Check with your supervisor." — existing `housekeeping.page.myRooms.emptySubtitle`, migrate into `EmptyState`'s `body` prop verbatim |
| Error state (my-rooms board query — new, genuine gap per CONTEXT.md) | New key `housekeeping.page.myRooms.loadError`: **"Couldn't load your rooms. Try again."** — mirrors the existing `housekeeping.roomStatus.error.failedToLoad`/`retry` shape (short problem statement + a `common.retry` or existing `retry` labeled button wired to the query's own `refetch`) |
| Error state (staff-list query in `HousekeeperBar`, if a genuine `isError` gap is confirmed during implementation) | New key `housekeeping.page.assignBar.loadError`: **"Couldn't load staff. Try again."** — same shape; only add if planner/implementer confirms the gap exists (CONTEXT.md flags this as a check-during-implementation item, not a confirmed gap) |
| Destructive confirmation | "Undo": the existing **inline two-tap confirm** pattern (tap "Undo" → button becomes "Confirm undo" in `--alert` red + a "Cancel" ghost button appears beside it) is this phase's confirmation approach for the one destructive-adjacent action in scope. This is an established codebase pattern (same shape as the existing "Done"/"Confirm done" two-tap on the same component) — v2 restyle preserves the exact two-tap mechanic, only updates surface tokens/spacing if touched at all |

No new destructive (delete/archive) actions exist in this phase's scope — `AssignmentSidebar`'s AI auto-assign and `PredictionPanel`'s reassign/escalate/acknowledge actions are all reversible operational actions, not data-destructive, and already have their own inline confirm-before-act UI (preserved exactly, per CONTEXT.md — visuals only, zero flow changes).
