<objective>
Close UX-02: shift-template dropdowns in Scheduling show no duplicate or leftover entries.

Root cause (confirmed by direct read this session): `supabase/migrations/005_scheduling.sql` defines `shifts` with no uniqueness constraint on `(tenant_id, department_id, name)` — only `PRIMARY KEY (id)`. `apps/api/routers/scheduling.py::create_shift()` (lines 71-86) does a plain `.insert()` with zero pre-check for an existing shift of the same name/department. Nothing prevents creating "Morning" twice for the same department (deliberate double-create, or a double-submit from a network retry / second tab — the Create button is only guarded by `disabled={isPending}` client-side, which does not cover that case). Once two shift rows share a name, both surface identically in `AssignShiftModal`'s Shift `<select>` and the "Manage Shifts" list, looking like duplicate/indistinguishable entries. `delete_shift()` is a hard DELETE with `ON DELETE CASCADE` on `shift_assignments.shift_id`, so a deleted shift does not leave orphaned assignment rows — "leftover" most likely describes the duplicate-creation scenario, not an orphan-row bug.

Purpose: prevent the duplicate from being creatable in the first place, at the API layer (no migration/schema change required — a partial unique index was considered but rejected because it risks failing to apply if a duplicate already exists in live data, and an application-level check is sufficient to satisfy "no duplicate or leftover entries").

Output: `create_shift()` rejects a request for a shift whose `(tenant_id, department_id, name)` already matches an existing *active* shift, with a clear 409 error instead of a silent second insert.
</objective>
