<objective>
Add a reset of the escalation watermark (`escalation_level=0`, `high_risk_since=None`) to every single-item action that should stop Plan 03's GM-escalation clock: `reassign_at_risk_room`, `escalate_at_risk_room`, `acknowledge_at_risk_room` (room-readiness, `housekeeping.py`), and `acknowledge_failure_prediction`, `create_work_order_from_prediction` (asset-failure, `assets.py`).

Purpose: AI-13 requires escalation to stop "the moment it is reassigned, acknowledged, or its risk drops below HIGH." Plan 02 handles the risk-drop case (inside the prediction engines). This plan handles the human-action case — without it, a supervisor/engineer who correctly responds to a HIGH-risk prediction would still see it auto-escalate to the GM an hour later purely because nobody happened to touch two fields that have nothing to do with the action they actually took. Placing the reset inside these five single-item coroutines (not in a new layer, not duplicated into the batch loop) means Phase 28's already-shipped batch endpoints (`batch_reassign_rooms`, `batch_acknowledge_rooms`, `batch_acknowledge_failure_predictions` — all confirmed to call these exact five coroutines per-row) get correct reset behavior automatically, with zero changes to their own code.
Output: Five reset call sites landed, with characterization tests proving each one clears the watermark from a pre-escalated fixture row.

Sequencing note: this plan depends on 29-02 (not just 29-01) because Task 1 extends `apps/api/tests/test_room_readiness_actions.py`, the same file 29-02 also extends (with a different set of tests, for `run_room_predictions`'s carry-forward behavior) — running both in the same wave would risk two agents editing the same file concurrently. 29-01's migration is still the real schema prerequisite; 29-02 is a sequencing convenience on top of that.
</objective>
