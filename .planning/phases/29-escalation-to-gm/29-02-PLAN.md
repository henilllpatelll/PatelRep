<objective>
Give both prediction engines the ability to persist an escalation watermark (`escalation_level`, `high_risk_since`) across their own regeneration cycles: `room_readiness_predictions` via upsert-merge omission (mirrors the existing `is_acknowledged` preserve/reset pattern), `failure_predictions` via explicit read-before-delete carry-forward (since that table is rewritten by delete-then-insert, not upsert).

Purpose: AI-13 requires escalation to "resume counting" only on a genuine fresh re-entry into HIGH, never reset merely because a cron cycle ran. Without this plan, Plan 03's cron would have nowhere reliable to read "how long has this been HIGH" from — `room_readiness_predictions` would lose the anchor to upsert-merge accidents if not explicitly preserved, and `failure_predictions` would reset the anchor to a fresh timestamp on literally every 30-minute regeneration (since it's fully deleted and reinserted every run), making the 60-minute threshold unreachable in practice for assets.
Output: `predictions.py` and `failure_predictions.py` correctly stamp/preserve/reset the two watermark columns; a characterization test pair per table proving preserve-while-HIGH and reset-below-HIGH.
</objective>

```python
def _carry_forward_escalation_watermark(hotel_id: str, asset_id: str, risk_score: int, previous_score: int) -> dict:
    """
    Read the previous unacknowledged failure_predictions row for this asset
    (before it gets deleted) and decide what escalation_level/high_risk_since
    the NEW row should carry, since this table is rewritten via delete-then-
    insert rather than upsert (no SQL merge semantics available).

    "Was this asset already HIGH last cycle" is decided from `previous_score`
    (the asset's own cached `failure_risk_score` from BEFORE this run's
    recompute), not from whether the previous failure_predictions row's
    high_risk_since happened to be non-NULL. The watermark columns can be
    NULL/0 even though the asset never left HIGH risk -- e.g. right after
    create_work_order_from_prediction resets escalation_level=0/high_risk_since=None
    on an unacknowledged row (Plan 04) without touching is_acknowledged, so that
    row is still picked up by the next regeneration. Deriving "was previously
    HIGH" from the watermark itself would misread that reset as "not HIGH last
    time" and incorrectly restart the 60-minute clock even though the asset's
    actual risk never dropped. previous_score is the correct, reset-proof
    signal for risk continuity.

    Returns a dict with exactly "escalation_level" and "high_risk_since" keys,
    ready to merge into the insert payload.
    """
    prev_pred = supabase.table("failure_predictions")\
        .select("escalation_level, high_risk_since")\
        .eq("tenant_id", hotel_id).eq("asset_id", asset_id).eq("is_acknowledged", False)\
        .maybe_single().execute()
    prev_row = prev_pred.data or {}
    prev_escalation_level = prev_row.get("escalation_level", 0)
    prev_high_risk_since = prev_row.get("high_risk_since")

    now_utc = datetime.now(timezone.utc)
    if risk_score >= 70 and previous_score >= 70:
        # still HIGH across this re-run (by the asset's actual risk score, not
        # by whether something already reset the watermark) -> carry forward
        return {"escalation_level": prev_escalation_level, "high_risk_since": prev_high_risk_since}
    elif risk_score >= 70:
        # fresh crossing -> stamp a new anchor
        return {"escalation_level": 0, "high_risk_since": now_utc.isoformat()}
    else:
        # below HIGH -> reset
        return {"escalation_level": 0, "high_risk_since": None}
```

Note the branch uses an explicit `previous_score` parameter — mirroring Sub-feature A's `previous_risk` signal — NOT a `was_high` flag derived from the previous `failure_predictions` row's own `high_risk_since`. The watermark columns are not a reliable "was this asset HIGH last cycle" signal on their own: Plan 04's `create_work_order_from_prediction` resets `escalation_level`/`high_risk_since` on an unacknowledged row without touching `is_acknowledged`, so a still-HIGH asset can show up at the next regeneration with a NULL `high_risk_since` even though its risk never dropped. `run_asset_failure_predictions` already computes `previous_score = asset.get("failure_risk_score") or 0` from the `assets` row (not from `failure_predictions`) at line ~421 for its own unrelated notify-trigger logic; `run_single_asset_prediction` needs one new line to compute the same thing from the `asset` dict it already fetches via `.select("*, asset_categories(...)")`. Both call sites already have (or can cheaply get) `previous_score` — there is no reason to fall back to a less reliable watermark-derived signal.
