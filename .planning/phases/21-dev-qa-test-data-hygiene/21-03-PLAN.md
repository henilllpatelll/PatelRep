Use ONLY stdlib `argparse` + the existing Supabase service-role singleton — no new dependencies.

Implement all of the following:

1. **CLI gating (dry-run is the DEFAULT, fail-safe):**
   `argparse` with a single `--execute` store_true flag. `dry_run = not args.execute`. The docstring must state: default = dry-run (safe); `--execute` = real deletes. Never make dry-run opt-in.

2. **Constants (transcribe from 21-ALLOWLIST.md — Plan 02's authoritative list):**
   - `PRESERVE = {"23264962-aa09-4e4f-a49d-fc345cc91414"}`  # active QA fixture
   - `DELETE_ALLOWLIST = { ...every non-fixture tenant UUID from 21-ALLOWLIST.md... }`
   - `EXCLUDE_TABLES = {"controlled_incidents", "controlled_incident_events"}`  # QA-03 append-only

3. **Guardrails (run before any DB write, in dry-run too):**
   - Assert `DELETE_ALLOWLIST` and `PRESERVE` are disjoint — abort if the fixture is in the allowlist.
   - Assert `DELETE_ALLOWLIST` is non-empty — refuse to run on an empty allowlist.
   - Cross-check via `mcp`-equivalent SDK query that every allowlisted UUID has `is_test = true` and that no `PRESERVE` UUID has `is_test = true`; abort if a mismatch is found. (This is the belt-and-suspenders intersection of the flag with the hardcoded constant per the locked decision.)
   - After computing per-table counts, assert that NO row outside `DELETE_ALLOWLIST` would be touched — every query is already `.in_("tenant_id", allowlist)`, so this is a structural guarantee; additionally verify the fixture's own child-row counts are excluded from the report.

4. **Table discovery (don't hand-maintain a list):**
   Discover every table carrying a `tenant_id` column via `information_schema.columns` (use the Supabase SDK against a helper view or an `execute_sql`-style RPC if available; otherwise fall back to a documented explicit list). Subtract `EXCLUDE_TABLES` and `tenants` itself. The script deletes CHILD data only and leaves the `tenants` row intact (per locked decision — no `--drop-tenant-row` option).

5. **Per-table scoped delete / count:**
   For each discovered table: in dry-run, `supabase.table(tbl).select("id", count="exact").in_("tenant_id", list(DELETE_ALLOWLIST)).execute().count`; in execute mode, `len(supabase.table(tbl).delete().in_("tenant_id", list(DELETE_ALLOWLIST)).execute().data or [])`. Follow the `.delete()...len(result.data)` precedent in `apps/api/routers/internal.py`.

6. **FK-safe delete ordering (REAL scope — not an afterthought; the dry-run does NOT exercise it):**
   Real deletes can hit `ON DELETE RESTRICT` FKs (e.g. `safety_training_assignments.course_id → safety_training_courses`, `emergency_drill_participants.drill_id → emergency_drills`) if a parent is deleted before its children. Implement ordering as a **fixpoint retry loop**: attempt each remaining table's delete; on a Postgres FK-violation (SQLSTATE 23503 / RESTRICT) defer that table; repeat passes until a full pass makes no progress. If tables remain when progress stalls, raise with the offending tables listed. This auto-handles ordering without hand-maintaining a topological sort and stays correct as the schema grows. In dry-run mode (pure counts) ordering is irrelevant — skip the retry loop.

7. **Report:** Print a per-table table of rows-would-delete (dry-run) or rows-deleted (execute), a total, the mode banner (DRY-RUN vs EXECUTE), and an explicit line confirming `controlled_incidents` / `controlled_incident_events` are excluded and zero rows outside the allowlist are affected.

Keep the file under ~200 lines. Do NOT invoke `--execute` anywhere in the code path by default. Do NOT delete the tenant row.
