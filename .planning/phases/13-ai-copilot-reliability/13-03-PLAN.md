<objective>
Close the last gap in the "reference" error-handling pattern and finalize cross-surface consistency (success criterion 3). `AICopilotBubble.tsx`'s `sendMessage` (lines 269-279) already catches failures and appends a visible inline chat bubble — but the catch is bare (`catch { ... }`) and always shows the hardcoded "Something went wrong. Please try again." even when a real, more specific `ApiClientError.message` is available (e.g. "AI service temporarily unavailable. Please try again later."). Worse, the four confirm handlers (`handleConfirmTasks`, `handleConfirmWorkOrders`, `handleConfirmGuestRequests`, `handleConfirmAssignments`, lines 281-300) have **no catch at all** — a failed `aiApi.confirmX(...)` call propagates up through `ConfirmView`/`TaskConfirmView`'s `try { await onConfirm() } finally { setConfirming(false) }` (also no catch), so the spinner silently resets to the unconfirmed state with zero visible explanation. This is exactly the "silent failure" pattern the whole phase exists to eliminate — on the one surface positioned as the reference pattern for the other two.

Critical constraint on the fix: `ConfirmView`/`TaskConfirmView` (`AICopilotBubble.tsx` ~lines 60-64, 87-90) run `try { await onConfirm(); setConfirmed(true) } finally { setConfirming(false) }` — `setConfirmed(true)` only fires if `onConfirm()` does NOT throw. If the confirm handlers below catch their error purely locally and swallow it (never rethrow), `await onConfirm()` resolves normally even though the backend call failed, and `setConfirmed(true)` fires anyway — producing a false "✓ N task(s) created" checkmark at the exact moment the inline chat bubble says it failed. That is the same fake-success bug class this phase exists to eliminate, reintroduced on the reference surface. The fix therefore requires each confirm handler to append the inline error bubble for visibility **and then rethrow** the error, so the parent's `await onConfirm()` still rejects, `setConfirmed(true)` is correctly skipped, and the existing `finally { setConfirming(false) }` resets the button to a retryable, non-confirmed state — not a "do not propagate" pattern.

This plan runs after 13-01 and 13-02 because it defines the final, audited version of the shared error-handling convention those two plans already established independently (`catch (err) => err instanceof ApiClientError ? err.message : localized fallback`), and because verifying "consistency across all 3 entry points" (success criterion 3) requires those two surfaces to already be fixed for comparison.

Purpose: The chat page — the most-used AI Copilot surface — must never leave a user staring at a silently-reset confirm button with no explanation, nor a falsely-confirmed checkmark when the action actually failed, and its pre-existing working behavior must not regress in the process.
Output: All chat-page AI interaction paths (send + all 4 confirm flows) surface real errors inline and correctly leave the Confirm button in a retryable state on failure; full regression pass proves fast-path/intent-parsing/SOP-Q&A/credit behavior is unchanged; final cross-surface consistency confirmed.
</objective>
