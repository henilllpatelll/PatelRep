<objective>
Fix the real defect behind AI-02: `handleAITriage` (`apps/web/app/(dashboard)/engineering/work-orders/page.tsx:306-330`) calls `aiApi.chat('Triage open work orders and suggest the safest floor order for engineers.', { source, work_orders })` with no `intent_hint`. That literal message scores 0 against every keyword list in `detect_intent()` (`apps/api/routers/ai_copilot.py`) and falls through to `intent = "general"` — a hardcoded canned string that makes zero LLM calls and never reads `request.context`, so the `work_orders` payload is silently discarded server-side. The result: a "successful" click always shows the exact same generic "AI triage applied" notice regardless of what was actually sent, while the honest, already-correct client-side deterministic sort in `sortWOs()` does all the real work.

Fix: add a dedicated `work_order_triage` intent instead of only re-styling the failure copy. The frontend now sends `intent_hint: 'work_order_triage'` in the chat context; `detect_intent()` already routes any supplied `intent_hint` straight through with no change needed there (`if intent_hint: return intent_hint`). A new rule-based branch in `ai_copilot.py` reads `request.context.work_orders` and returns a genuine, backend-computed summary (overdue count, unassigned count, suggested floor order) as `response.data.message` — mirroring 13-01's precedent of a pure rule-based, zero-credit, zero-LLM endpoint (`suggest_assignments`). This keeps the feature testable end-to-end on localhost without live OpenAI/Anthropic credentials (per this project's current scope: no live API keys are configured locally) and satisfies AI-02 success criterion 2 literally — the engineer receives an actual triage result, not a re-styled failure notice — without expanding this reliability phase into a full LLM-backed feature build.

The already-correct client-side deterministic sort in `sortWOs()` still runs unconditionally in the `finally` block regardless of outcome — that part is real, working logic and does not change; only the notice's content must now reflect genuine backend analysis, and its styling must stop disguising failure as success.

Establishes and reuses the canonical error-handling pattern from 13-01 (`catch (err) { ... err instanceof ApiClientError ? err.message : fallback ... }`) so this surface and the housekeeping surface behave identically per success criterion 3.

Purpose: An engineer must be able to tell, at a glance, whether the AI triage call actually worked or failed — a failure must never be worded as if it "applied" — and when it succeeds, the notice must reflect the real work orders on the board, not a static string.
Output: A new `work_order_triage` backend intent returns a genuine, context-derived summary; `handleAITriage` sends the intent hint and sets a typed `{ message, isError }` notice from the real response; the notice box renders distinct alert styling on failure; adjacent Engineering surfaces confirmed unaffected.
</objective>
