<objective>
Fix LOSTFOUND-01: deleting a Lost & Found item that has custody history throws a foreign-key error and the record is permanently stuck.

Purpose: `lost_found_custody_events.lost_found_item_id` is declared `ON DELETE RESTRICT` (migration 072), so Postgres refuses to delete any item that has custody events — and every item gets an `intake` custody event at creation, so effectively no item with history can ever be deleted. A second layer also blocks the obvious workaround: the `lost_found_custody_events_immutable` trigger fires `BEFORE UPDATE OR DELETE`, so explicitly deleting the child rows first also raises "Guest recovery and custody events are append-only." Both layers must be addressed for the delete to succeed.

Output: A migration switching the FK to `ON DELETE CASCADE` and recreating the immutability trigger as `BEFORE UPDATE` only (preserving content-tamper protection while allowing a parent-item delete to cascade), plus regression tests. No router code change is required — the existing `delete_lost_found_item` endpoint works once the DB permits the cascade.
</objective>

  <files>supabase/migrations/087_lost_found_custody_cascade.sql</files>
  <action>
    Create `supabase/migrations/087_lost_found_custody_cascade.sql` doing two things:

    1) Change the child FK from RESTRICT to CASCADE so deleting an item removes its custody trail:

        ALTER TABLE public.lost_found_custody_events
          DROP CONSTRAINT lost_found_custody_events_lost_found_item_id_fkey;
        ALTER TABLE public.lost_found_custody_events
          ADD CONSTRAINT lost_found_custody_events_lost_found_item_id_fkey
          FOREIGN KEY (lost_found_item_id)
          REFERENCES public.lost_found_items(id) ON DELETE CASCADE;

       (Postgres default constraint name is `<table>_<column>_fkey`; confirm against migration 072
       which uses the default naming. If the name differs, query pg_constraint or match 072.)

    2) Recreate ONLY the lost_found custody immutability trigger to fire on UPDATE, not DELETE, so
       the cascade is permitted while contents remain tamper-proof (append-only). Do NOT touch the
       other three triggers that share `reject_guest_recovery_mutation()`
       (guest_request_events, guest_messages, guest_recovery_actions) — leave them exactly as-is:

        DROP TRIGGER IF EXISTS lost_found_custody_events_immutable
          ON public.lost_found_custody_events;
        CREATE TRIGGER lost_found_custody_events_immutable
          BEFORE UPDATE ON public.lost_found_custody_events
          FOR EACH ROW EXECUTE FUNCTION public.reject_guest_recovery_mutation();

    Header comment must document the deliberate tradeoff (this is the design decision for
    LOSTFOUND-01, which was left to Claude's discretion): custody events remain immutable to
    UPDATE (you cannot alter recorded history), but deleting an entire item to correct a mistaken
    record cascades and removes that item's custody trail — matching the requirement's wording
    "permanently delete ... to correct a mistaken record." Explicit child-row cleanup in the
    router was rejected because the BEFORE DELETE trigger would block it anyway; CASCADE + an
    UPDATE-only trigger is the minimal correct fix.

    Follow the sequential migration convention (next free number after 086, which the logbook plan
    reserves — this plan owns 087). Do NOT apply the migration to the remote Supabase project as
    part of this plan.
