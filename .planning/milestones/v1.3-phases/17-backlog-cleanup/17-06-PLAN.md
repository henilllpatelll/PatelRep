<objective>
Close UX-06: Room History populates with actual room history data.

**This is a MEDIUM-confidence hypothesis, not a confirmed bug** (per 17-RESEARCH.md) — the drawer-side implementation is NOT missing (`RoomDetailDrawer.tsx` already fetches and merges 5 sources: room-history notes/status-changes, work orders, guest requests, tasks, clean sessions, with a correct empty-state fallback only when all 5 are empty). So the reported symptom, if real, must be a backend data/filtering issue, not missing wiring. Two concrete candidates were found by direct code read:

1. **`stay_reset_at` over-triggers.** `GET /rooms/{room_id}/history` (`apps/api/routers/rooms.py` lines 1004-1030) filters `room_status_history` to `created_at >= stay_reset_at` whenever `room_status.stay_reset_at` is set. That's set correctly on a genuine passed-DEP-inspection event (`housekeeping.py:1445-1449`, `rooms.py:212-216`), but is *also* set by the bulk Opera-occupancy-import path (`housekeeping.py` — the `if resolved_status == "INSPECTED": update_data["stay_reset_at"] = now_iso` line inside the occupancy-import upsert) whenever the imported/resolved status happens to be INSPECTED — a much broader condition than "housekeeping just completed a fresh clean+inspection right now." If occupancy import runs routinely, the visibility boundary keeps rolling forward, hiding real prior status-history/note entries even though the room's actual clean history didn't change.
2. **Missing `user_profiles` embed.** The query is a bare `.select("*")` with no join, so actor attribution (`entry.actor_name` / `entry.user_profiles.preferred_name`, referenced by `RoomDetailDrawer.tsx` lines 126, 1071) is never present in the response.

Purpose: **do not blindly implement candidate (1) as a fix.** Reproduce it live first, because the "Room History" section it affects is only ONE of the drawer's 5 merged sources (WOs/guest-requests/tasks/clean-sessions are separate, un-gated queries) — a room with real WOs/tasks would show *some* history even if candidate (1) is real, so "doesn't populate" could also mean something else entirely (a role-gating surprise, a room genuinely having zero history, or a frontend staleness bug not found in this research pass).

Output: a documented diagnostic finding (confirmed or ruled out), followed by the appropriate fix — either narrowing the bulk-import `stay_reset_at` trigger, adding the missing actor-attribution embed, both, or (if the hypothesis is ruled out) an investigation writeup pointing at the real cause for follow-up.
</objective>
