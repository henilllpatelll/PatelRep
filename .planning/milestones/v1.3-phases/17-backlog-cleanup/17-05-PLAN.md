<objective>
Close UX-05: the Guest Request drawer includes status-advance actions, not just view.

Root cause (confirmed by direct read this session): `GuestRequestDrawer.tsx` (393 lines, full file read) has a message thread + reply composer, a satisfaction-score widget (only after resolved), and an internal-note form — but no status-transition controls at all. The status state machine (`open → acknowledged → dispatched → arrived → guest_contacted → resolved → verified`) is fully implemented, but only on the kanban card component in `GuestRequestsPage.tsx`: per-status "Advance" buttons (lines 109-145, e.g. `onClick={() => onAdvance(request.id, 'acknowledged')}`), a `handleAdvance` callback (lines 187-190), and `updateMutation` (lines 172-179) which calls the real `guestRequestsApi.transitionRequest(id, { status })` → `POST /guest-requests/{id}/transition`. The drawer (opened via `onCardClick` → `setDrawerRequest(r)`, line ~254-256) is a separate component tree that never receives `onAdvance`/`updateMutation` — a user who opens the drawer for full detail has no way to advance status without closing it and clicking the small button on the card behind it.

Purpose: give the drawer the same real transition capability the card already has, reusing the exact same mutation and query-invalidation the card uses — no new backend work, no new state machine, just wiring the existing one into a second surface.

Output: `GuestRequestDrawer` gains an `onAdvance` prop (mirroring the card's) and renders the same per-status action button(s); `GuestRequestsPage` passes its existing `handleAdvance`/`updateMutation.isPending` into the drawer instead of only the card.
</objective>
