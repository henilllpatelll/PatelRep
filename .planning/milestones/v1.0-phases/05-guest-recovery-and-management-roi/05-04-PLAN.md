<objective>
Close the lost & found retention loop: start a fixed 90-day clock at intake, have a daily cron flag expired items for manager review without disposing of anything, expose a `disposition_due` filter so managers can find them, and prove the disposition-approval role set is exactly gm + housekeeping_supervisor + front_desk.

Purpose: `retention_due_at` and `disposition_approved_by` have existed in the schema since migration 072 and are completely unused by code today — the retention clock does not tick and nothing ever surfaces for review.
Output: `POST /v1/internal/lost-found/retention-check`, a `disposition_due=true` list filter, cron registration, and `apps/api/tests/test_lost_found_retention.py`.
</objective>

1. `apps/api/routers/internal.py` — add near the other daily handlers:
```python
@router.post("/lost-found/retention-check")
async def check_lost_found_retention(x_cron_secret: str = Header(None)):
    """D-11: flag expired unclaimed items for manager review. Never auto-donates or discards."""
    verify_cron(x_cron_secret)
    now = datetime.now(timezone.utc).isoformat()
    flagged = 0
    try:
        due = supabase.table("lost_found_items").select("id, tenant_id").eq(
            "status", "unclaimed"
        ).lt("retention_due_at", now).is_("disposition_flagged_at", "null").execute().data or []
        for item in due:
            supabase.table("lost_found_items").update(
                {"disposition_flagged_at": now}
            ).eq("id", item["id"]).eq("tenant_id", item["tenant_id"]).execute()
            flagged += 1
    except Exception as exc:  # noqa: BLE001
        logger.error("lost-found retention check failed: %s", exc)
        _record_cron_run("lost-found.retention-check", error=str(exc))
        raise HTTPException(status_code=500, detail="Retention check failed") from exc
    _record_cron_run("lost-found.retention-check")
    return {"status": "ok", "flagged": flagged}
```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions → `POST /v1/internal/lost-found/retention-check` | Unauthenticated except for a shared secret header; runs with service-role database access across all tenants |
| authenticated staff → `POST /v1/lost-found/{id}/custody-events` | Role + tenant boundary controlling release and disposition of a guest's property |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-04-01 | Spoofing | `check_lost_found_retention` cron endpoint | mitigate | `verify_cron(x_cron_secret)` is the first statement; a mismatched or absent `X-Cron-Secret` raises 401 before any query. Covered by `test_retention_check_rejects_bad_cron_secret` |
| T-05-04-02 | Elevation of Privilege | Automation disposing of guest property without a human | mitigate | D-11: the cron writes only `disposition_flagged_at`. `status`, `disposition_approved_by`, and `lost_found_custody_events` are untouched — asserted by `test_retention_check_does_not_change_status_or_create_custody_event` |
| T-05-04-03 | Elevation of Privilege | Unauthorized role approving a disposition | mitigate | The existing `{"front_desk", "housekeeping_supervisor", "gm"}` gate in `record_lost_found_custody_event` is left byte-for-byte unchanged and now has explicit positive and negative tests (D-12) |
| T-05-04-04 | Information Disclosure | Cross-tenant flagging or listing | mitigate | The cron's update carries `.eq("tenant_id", item["tenant_id"])` taken from the selected row, and the list filter runs inside the existing `.eq("tenant_id", current_user.hotel_id)` query chain |
| T-05-04-05 | Tampering | Client-supplied retention date shortening the clock | mitigate | `retention_due_at` is computed server-side from `datetime.now(timezone.utc) + timedelta(days=90)`; the request model has no such field and the router never reads one |
| T-05-04-06 | Repudiation | Silent cron failure hiding overdue items | mitigate | `_record_cron_run` is called on both success and error paths, feeding the existing `/health` cron-staleness surface built in Phase 0 |
| T-05-04-07 | Denial of Service | Unbounded per-item update loop on a large backlog | accept | Scale is 50-150 room hotels; the `disposition_flagged_at IS NULL` guard makes the loop shrink to zero after the first run, and `idx_lost_found_retention_due` covers the selection |
</threat_model>
