# Phase 3: Texas compliance and staff safety - Context

**Gathered:** 2026-07-21
**Status:** Ready for planning

<domain>
## Phase Boundary

Make Texas-specific staff-safety compliance operational by building three vertical web + API slices on top of the already-applied Phase 3 schema (migration `070_texas_safety_compliance.sql`):

- **3A — Human-trafficking training:** approved provider/course metadata, covered-role assignment, new-hire deadline + annual recurrence, completion + certificate upload, signage verification checklist, reminders/escalations, per-employee/hotel compliance status, and an inspector-ready export.
- **3B — Controlled incident records:** immutable base incidents (guest injury, employee injury, chemical exposure, sharps/body-fluid, security, privacy, discrimination, police/fire, life-safety impairment) with append-only corrections/review/follow-up/closure, retention policy, and legal hold.
- **3C — Hazard communication and emergency evidence:** chemical inventory + SDS linkage, PPE/secondary-label checks, spill/exposure procedures, emergency plan distribution + acknowledgement, emergency contacts/roles, drill records + staff-accountability evidence, and a **designed (not live-wired)** webhook intake contract for third-party staff-safety devices.

**Out of scope:** building any hardware; live third-party device intake; Phase 4–6 programs (PM/housekeeping programs, guest recovery, PMS/AI expansion); Stripe/AI-provider-dependent paths; Vercel repair; all `apps/mobile/` work.

</domain>

<decisions>
## Implementation Decisions

### Slice order and webhook scope
- **D-01:** Build in order **3A (training) → 3B (incidents) → 3C (hazcom + emergency)**. Training leads because it is the hardest Texas legal requirement and the highest daily-value surface; incidents are self-contained immutability; hazcom+emergency is the broadest.
- **D-02:** The third-party staff-safety-device webhook is **design-only** this phase: define a feature-flagged intake contract/stub (mirroring the Opera integration feature-flag pattern) that documents how a device panic event would map to a controlled incident + evidence record. Do **not** wire live intake — no partner or hardware exists, and the path is not locally testable. No hardware is built.

### Incident reporting access and privacy
- **D-03:** **Any authenticated staff can FILE a controlled incident** (housekeeper and engineer included) — fast injury/exposure reporting is the priority. Creation is gated by `require_role()` for authenticated users, not restricted to management.
- **D-04:** **Viewing full incident detail is restricted to management roles** (`gm`, `chief_engineer`, `housekeeping_supervisor`). A filer may retrieve incidents they themselves created. Sensitive types (`guest_injury`, `discrimination`, `privacy`) are not visible to non-management floor staff. (Single management-view tier chosen over per-type GM-only branching for simpler, auditable RBAC.)

### Training assignment generation
- **D-05:** Assignments and reminders are **auto-generated by a cron**, not manually assigned. A scheduled job creates new-hire assignments (honoring `safety_training_courses.new_hire_deadline_days` on staff creation) and annual-recurrence assignments (`recurrence_months`), and queues reminders/escalations. Reuse the Phase 2 retraining-assignment RPC pattern and `notification_deliveries` — do not build a parallel scheduler. This directly satisfies the exit criterion that overdue items automatically reach the correct supervisor.
- **D-06:** The cron endpoint follows the existing `routers/internal.py` `X-Cron-Secret` convention and writes to `cron_health` like every other job (migration 068).

### Bilingual floor scope
- **D-07:** Phase 3 **introduces web i18n for the first time**, scoped to **staff-facing safety actions only**: training acknowledgement, incident filing, safety-information retrieval, and drill acknowledgement get EN + ES. GM-facing config, compliance dashboard, and inspector export **stay English**.
- **D-08:** General engineering-component web i18n remains deferred to Phase 4 (the bilingual floor contract). Phase 3 does not retrofit existing English-only screens beyond the safety surfaces above.

### Carried forward from Phase 2 (locked — not re-discussed)
- **D-09:** Reuse the evidence platform: `evidence_records` + private `evidence-files` bucket with short-lived signed URLs for all certificates, SDS files, and incident attachments. Never expose public storage URLs.
- **D-10:** Reuse Phase 1/2 `operational_audit_events` (append-only) for material changes and structured reason codes; reuse `notification_deliveries` for reminder/escalation channel + outcome history. No parallel audit or notification mechanism.
- **D-11:** Every table and query is tenant-scoped (`.eq("tenant_id"/"hotel_id", ...)`), backed by RLS, and every mutation gated with `require_role()`.
- **D-12:** **Security discipline (migration 079 lesson):** every new `SECURITY DEFINER` RPC must `REVOKE EXECUTE FROM anon, authenticated, PUBLIC` and `GRANT EXECUTE TO service_role` only — `REVOKE ... FROM PUBLIC` alone is insufficient against Supabase's default direct grants.
- **D-13:** Web + API only; no `apps/mobile/` changes. No core path may depend on local AI-provider or Stripe credentials.
- **D-14:** **Plan-review gate:** stop after planning and present the complete Phase 3 plan for user review before any execution begins.
- **D-15:** Build complete vertical web + API slices with focused tests; do not create tables or screens disconnected from an operational workflow.

### Claude's Discretion
- Exact route shapes, schema refinements on top of migration 070, per-mutation role sets, cron cadence, checklist storage shape (evidence record vs. dedicated column), and component layout — select from existing project patterns as long as the locked contracts above hold.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- Migration 070 tables already exist with RLS + append-only triggers — Phase 3 is primarily routers + web + tests, not new data modeling.
- Phase 2 `evidence_records` + private bucket signed-URL flow covers all Phase 3 attachments (certificates, SDS, incident photos).
- Phase 2 exception-engine + reminder/escalation machinery is the template for training due-state and missing-follow-up-evidence escalation.
- `routers/internal.py` cron pattern + `cron_health` cover the auto-assignment job.

### Established Patterns
- API handlers: direct Supabase SDK, explicit tenant filter, `require_role()` gate, `{ "data": ... }` responses; lists add `meta` pagination.
- New routers register in `apps/api/main.py` with a `/v1/...` prefix.
- Append-only correction model: `controlled_incidents` base row is immutable (trigger-enforced); all changes append `controlled_incident_events`.
- Web state: React Query for server data, Zustand for auth; no Realtime for these standard screens (pull/refresh).

### Integration Points
- Training certificates and SDS files link to `evidence_records` (FK already present in migration 070).
- New-hire assignment cron hooks into staff creation (`staff.py`) and the covered-roles array on `safety_training_courses`.
- Compliance status/export surfaces reuse (or extend) the Phase 2 GM evidence dashboard rather than creating a separate compliance silo.
- Web i18n is a **new** mechanism on web — no existing `t()` in web components; this phase establishes the pattern for the scoped safety surfaces.

</code_context>

<specifics>
## Specific Ideas

- The compliance test for 3A is the exit-criteria state machine per employee: **compliant / due-soon / overdue / not-applicable**, visible by employee and hotel, with an inspector-ready export.
- 3B's non-negotiable: controlled incidents cannot be silently deleted or rewritten — corrections are append-only events, retention + legal hold honored.
- 3C's floor outcome: staff can retrieve the applicable safety information (SDS, PPE, spill/emergency procedures) in English and Spanish, and missing follow-up evidence automatically reaches the correct supervisor.
- The staff-safety-device webhook is a **contract on paper + feature-flagged stub**, matching how Opera Cloud is feature-flagged for pilot — no live intake, no hardware.

</specifics>
