## Gap Found and Resolved In-Session

### Migration 087 was not applied to production (blocked LOSTFOUND-01)

Initial audit found: the code fix and tests were correct, but the live Supabase database (project `oacnwalhcpqdabivweki`) still had:
- `lost_found_custody_events_lost_found_item_id_fkey` as `ON DELETE RESTRICT` (should be `CASCADE`)
- `lost_found_custody_events_immutable` trigger firing on `BEFORE UPDATE OR DELETE` (should be `BEFORE UPDATE` only)

Confirmed via `supabase list_migrations` — no `086` or `087` entries present at time of audit. Every Lost & Found item gets an `intake` custody event at creation, so **any** permanent-delete attempt on **any** item would have raised a raw, unhandled Postgrest 500 in production.

**Resolution:** With user authorization, applied both migrations to the production project via Supabase MCP (`apply_migration`), then verified the actual schema state directly via SQL rather than trusting the migration-history log alone:
- `pg_constraint.confdeltype` for the FK = `'c'` (CASCADE) — confirmed
- `pg_trigger.tgtype` for the immutability trigger = `19` (BEFORE + UPDATE + ROW, no DELETE bit) — confirmed narrowed correctly
- Logbook backfill: 0 of 1 production `logbook_entries` rows mismatched against hotel-local recomputation — confirmed
- `get_advisors(security)` re-run post-migration: no new advisories introduced by either DDL change (pre-existing GraphQL anon-exposure lint findings on both tables are unrelated and pre-date this milestone)

### Migration 086 (historical backfill) — also resolved

Applied alongside 087. Was lower severity to begin with (new entries were already correctly dated at the application layer), but is now fully current with 0 mismatched rows.
