## Cross-Phase Integration Check

Spawned `gsd-integration-checker` against the actual current codebase (not phase-summary prose) to check wiring at the seams between phases 18-22. Findings, independently re-verified against live source by the orchestrator:

### 1. ⚠ CRITICAL GAP — `chief_engineer` role: creatable but broken end-to-end

- **What broke:** Phase 20's `supabase/migrations/092_restore_chief_engineer_role.sql` restores `chief_engineer` as a fully live, creatable role — the migration's own comment documents it as already wired through `routeGuard.ts`, staff creation, and 15+ backend RBAC gates (`safety.py`, `programs.py`, `evidence.py`, `ai_copilot.py`, `assets.py`, `integrations.py`), just blocked at the DB `CHECK` constraint until this migration.
- **What Phase 19 got wrong:** `apps/api/core/roles.py` (introduced by Phase 19, one phase *before* migration 092 landed) hard-codes `ALL_ROLES`/`ALL_STAFF_ROLES` as 5 roles, explicitly excluding `chief_engineer`, with a comment claiming it "can no longer occur in a live JWT" — internally inconsistent with the same file's `MANAGER_ROLES`/`PROGRAM_MANAGER_ROLES`, which already include it.
- **Confirmed live consequence:** `apps/api/routers/hotels.py:117,193` gates `GET /hotels/{hotel_id}` and `GET /hotels/{hotel_id}/stats` on `ALL_STAFF_ROLES` — a `chief_engineer` JWT now gets 403 on both.
- **Confirmed live consequence #2:** `apps/web/app/(dashboard)/dashboard/page.tsx`'s role switch (lines 150-167) has cases for housekeeper/housekeeping_supervisor/engineer/front_desk/gm only; `chief_engineer` falls to `default: "No dashboard available for your role."` — even though `apps/web/components/dashboard/ChiefEngineerDashboard.tsx` exists fully built (confirmed via grep: exactly one match in the whole repo — its own definition, never imported).
- **Confirmed not caught by Phase 20's own tests:** `e2e/20-verify-rbac.spec.ts` only exercises `/engineering/work-orders` for the chief_engineer button-gate assertion, never `/dashboard` — so the phase's own verification had no way to see this.
- **Net effect:** a hotel that creates a chief_engineer user (the entire point of Phase 20's fix) gets a user who logs in successfully, per `routeGuard.ts` is allowed onto `/dashboard`, `/engineering`, `/scheduling`, `/ai`, `/sop`, `/logbook`, `/reports` — and lands on a broken empty homepage, with two of those adjacent API calls (`/hotels/{id}`, `/hotels/{id}/stats`) now 403ing.
