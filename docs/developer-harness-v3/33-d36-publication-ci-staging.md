# Developer Harness V3 — 33 D3.6 publication, exact-candidate CI, staging and base advancement

All SIMULATED (`orchestrator/sim/sim-github.mjs` models the audited workflow semantics, doc 31) and INACTIVE. The controller is `delivery/controller.mjs`; it uses no model.

## 1. Publication and PR management
* One task-owned branch `dh3/<task>` (deterministic, unique, immutable in `deliveries`); one PR per task (`pr:<task>` idempotency key, `pr_number` set once from an authenticated observation, a database-unique column). No force push, no push to `main`, never a history rewrite: every push is fast-forward from a sha this task itself published (`expected_old`), and the remote ref is re-observed immediately before dispatch.
* Before any mutation: a head on the branch that V3 never pushed (e.g. the Release Engineer) or a PR the publisher did not create ⇒ ONE owner decision; never adopted, never overwritten.
* Candidate facts are derived by the trusted fact source, never from the session; the evaluator checks scope, protected/root-of-trust paths, migrations (historical immutability, ordering, base currency), the customer Agent Harness tripwire, credential environment and special file modes on the RE-DERIVED change set. The engine's candidate checks (secrets, instruction/configuration files, customer-agent paths) already ran before the handoff.
* The publication receipt is issued by the `trusted_publisher` issuer from its own authenticated read of the remote ref (and PR ownership), never from the push response.
* Draft PR first; it is marked ready only at `merge_eligible` (`mark_pull_request_ready`, which requires CI evidence) — for human review, never for an automatic merge.
* **Finding:** a task that adds a migration can never publish in D3.6. The trusted task authority (`authorityOf`) carries no `migrations_authorized` / `protected_paths_authorized` flag, so the evaluator fails closed (`MIGRATION.NOT_AUTHORIZED_BY_TASK`). Correct by design; an owner-authorized flag is a future authority change (residual R-30).

## 2. Exact-candidate CI (`delivery/required-checks.mjs`, `delivery/diagnostics.mjs`)
* Required: `CI Gate` (ci.yml) and the four Mobile CI checks (mobile-ci.yml), each from app 15368, a run of the expected workflow with event `pull_request` and the task branch, on the EXACT head, latest run and attempt. Spoofed (other app), stale (older head or attempt), duplicate (two results for one attempt ⇒ ambiguous ⇒ fail), skipped/neutral (never success), cancelled and missing are distinct states; CI Gate already requires every need to be exactly `success`.
* Pending ⇒ deterministic polling with persisted, capped back-off. Missing beyond 30 min ⇒ technical suspension. GitHub rate limits ⇒ wait to the reported reset, no budget consumed.
* Failure ⇒ the verifier fetches bounded logs, REDACTS them (credentials, auth headers, userinfo URLs, JWTs, opaque tokens) and classifies deterministically: transient (runner/network/registry/rate limit/deploy infrastructure), genuine (test/type/lint/build/migration/smoke), protected control plane (frozen-file guard, workflow contracts), unknown (= genuine). Fingerprints (never logs) are persisted per run/attempt/job.
* Transient ⇒ the verifier issues a single-use `ci_failure_diagnosis`; the publisher re-runs the failed jobs (`rerun_ci_jobs`, P7); ≤2 per candidate, then a cooled-down technical suspension (infrastructure, not code). Genuine ⇒ `remediation(CI_FAILED)` with a fenced, labelled-untrusted, redacted excerpt; the new candidate is re-tested, re-reviewed, re-published and gets fresh CI and staging; every result of the old head is invalidated. Protected control plane ⇒ terminal technical suspension: a protected proposal, never a routine repair. Workflows and tests are never weakened.

## 3. Staging
* One V3-side shared-staging reservation (database-unique; `held` or `unresolved`), acquired BEFORE a push (a push starts CI, which starts staging), re-bound to the owner's current candidate, released only when an authenticated observation shows no queued or running staging run of the task and no unresolved staging intent. An unresolved owner keeps it. Other V3 tasks wait in `publishing` (nothing pushed).
* Staging Gate accepted only for the exact head, from app 15368, the staging workflow, with `details_url` = its run, run conclusion success, and the PR head re-checked at read time (audit gap 2).
* Displaced/never-started runs ⇒ re-dispatch (`dispatch_staging_candidate`, P7, authorized by a single-use `staging_admission`) ONLY when the shared group is idle, so V3 never displaces anyone's pending run; ≤2 per candidate. Deployment-infrastructure failures ⇒ re-dispatch; migration-plan and smoke failures ⇒ `remediation(STAGING_FAILED)`. No database or migration action exists outside the trusted staging workflow; production credentials are never involved.

## 4. Base advancement (strict ruleset)
At `merge_eligible`, a newer main (from a verified observation) ⇒ the trusted git merges it into the task branch in a task-owned worktree: clean ⇒ a NEW candidate on a new base generation (`deliveries.generation`; the submitted base stays immutable task identity and the authority base) ⇒ `head_changed` ⇒ `testing` ⇒ fresh tests, reviews, task authority for the new base, publication (fast-forward), CI, staging. A newer base is never verified by the merge itself. Conflicts in protected, migration or out-of-scope files ⇒ terminal suspension (never auto-resolved); conflicts in task files ⇒ fail closed under the authoritative lifecycle, `base_conflict_rebuild` (P6v2) under the proposal. ≤3 base updates per 24 h. A new migration on a stale base is refused by the evaluator (`MIGRATION.BASE_NOT_CURRENT`) and triggers the base update first. The dependency basis is carried to the new candidate (a base update of THIS task is not a dependency change).

## 5. Remediation F1 (independent verification): the LATEST applicable run decides
`checkState` used to choose among the checks that EXISTED, so an older run's success survived a newer same-SHA run that was queued, running, cancelled, failed or re-attempted without a result (reproduced; evidence file `d36-remediation-reproductions-BEFORE-FIX-SIMULATED.txt`). Now:
1. **Applicable runs** = the expected workflow, an expected event, the exact head SHA, the expected branch (CI) or PR (staging). The newest (created_at, then id) is THE run. Runs of another workflow / event / branch / head / PR never mask an older result and never count.
2. **The verdict is that run's check at the run's latest attempt**, from the pinned app (15368), exactly one. A run that has reported nothing is `pending` while it runs; once completed it is `cancelled` / `skipped` / `failed` by its own conclusion, or `missing` when it completed successfully without reporting the check. Duplicate trusted results for one attempt stay `ambiguous`; spoofed checks are still counted and ignored.
3. **Partial re-run ("re-run failed jobs")** is genuinely supported: a job that already succeeded keeps its earlier-attempt result, so an earlier-attempt SUCCESS from the pinned app is carried over only when the run's latest attempt COMPLETED with conclusion success and the highest earlier attempt that reported the check succeeded (a later attempt that reported it shadows it). A running or failed latest attempt carries nothing. This relaxes nothing else: every required check must still be `success`. (The live reader must confirm GitHub's exact shape for carried-over jobs before activation: G-REMOTE-READER.)
4. **Staging** uses ONE function, `stagingGate`, for the delivery observation, the `staging_gate` issuance and the final `delivery_verification`: staging runs of THIS PR only, the same latest-run rule, and provenance (run completed with conclusion success, its PR equals the PR, the result points at that run). Before the fix the verification checked only the state, not the PR association or provenance the gate issuance checked.
