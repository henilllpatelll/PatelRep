## 2. Ledger semantics

* **Durable**: WAL, `synchronous=FULL`, foreign keys, schema `user_version` with ordered migrations (a newer database is refused), `quick_check` on open, 512 MB cap, 1 MB per JSON blob, 20 000 events per task.
* **Immutable identity**: triggers forbid updating a task's repository, base, requirements, scope, acceptance or risk class and forbid deleting tasks, events or evidence. Requirements are digest-bound; `requirementsIntact()` is re-checked before every session and every restore.
* **CAS**: every lifecycle event runs the reducer inside `BEGIN IMMEDIATE` and updates the row `WHERE state_revision = <judged revision>`. Stale revision/token and idempotency conflicts are rejected; replays older than the reducer's window are caught by `UNIQUE(task_id, idempotency_id)`.
* **One reasoning slot** across all tasks and reviewers is a *partial unique index* (`leases … WHERE state IN ('active','termination_unverified')`), not just code. A slot is released **only** after termination is independently verified.
* **Fencing**: the task's token advances only through the reducer's `worker_recovered`, once per recovery. A clean renewal does not advance it.
* **Evidence**: accepted through the D3.2 verifier inside one transaction; nonce→digest table (same nonce+digest = idempotent, different digest = conflict); `consumeAll` is all-or-none and one-time; a head change invalidates candidate-bound evidence and open reviews.
* **Remote effects** (verification round F3): `beginIntent` consumes evidence and records the intent in ONE transaction; **dispatch, retry and creation all re-validate every ledger binding listed here** — task not cancelled, candidate SHA *and tree*, active policy revision, fencing epoch, creating lease, evidence validity *and expiry*, the action's required evidence kinds, that **every cited evidence SATISFIES** (D3.2 `isSatisfying`: verdict `pass` and no open critical/high finding — an authentic failed test, failed review or review with open mandatory findings is recorded by the store but never authorizes; F3b), and (for dispatch) the action's activation. `dispatched` becomes `uncertain` at restart; an uncertain intent is reconciled **only** by an explicit, authoritative, subject-bound observation (anything else stays uncertain and authorizes nothing). A retry never reuses expired or invalid authorization; a NEW authorized intent supersedes a PROVEN-absent one (`supersedes`, fresh evidence, old intent permanently non-retryable). D3.4 activates no action, so nothing can be dispatched; there is no GitHub code. This is the interface D3.6 must use.
* **Backup**: `VACUUM INTO` + sha256 sidecar + read-only verification; restore only produces a verified candidate file, never overwrites the live ledger.

## 3. One task, end to end

`submitted → queued → planning → implementing → testing → independent_review → security_review → publishing`, ending at a **verified delivery handoff** (`handoff_ready`), never `completed`.

1. **Admission** before any stage: `requirementsIntact`; the single slot; Resource Governor `admit` (memory/CPU/disk/pressure, guest metrics); for AI stages the Subscription Governor `admitAiWork` (extra usage verified-off and fresh, login valid, shared-headroom, retry time). Not admitted ⇒ `waiting_resources` / `waiting_subscription` / `waiting_external` with a wake-up time; the engine resumes by itself. Owner-only conditions (expired login, unverified extra usage, unauthorized billing, tampered requirements) ⇒ genuine `blocked` with ONE actionable outbox package.
2. **Routing** (`routing.mjs`): planning/implementation Sonnet medium (complex: Sonnet high; architecture or escalated remediation: Opus high); independent review Sonnet high; security review Opus high; summarization Haiku low (non-authoritative). Scheduling, authorization, quota waiting, monitoring, evidence verification and testing use **no model**. A mandatory security review is **never downgraded**: it waits. `--fallback-model`, API keys, base URLs, bypass, alternative accounts are refused outright.
3. **Session** (`session-runner.mjs`): lease → worker ready → prompt from the ledger → work units (≤20 turns / 30 min, configurable) → telemetry fed through the D3.3 parser → init verified (no API-key source, pinned CLI, `dontAsk`) → requested vs actual model verified → governor updated. The session's *claims* are never used: the candidate is re-derived by the controller's git adapter, scope/secret/customer-agent/historical-migration checked on the re-derived path list.
4. **Testing** is deterministic. A passing run is signed by the `orchestrator` issuer process; a failing run enters `remediation` with the failure as fenced untrusted data.
5. **Reviews**: a fresh context each, read-only candidate, enforced independently (the controller recomputes the tree digest after the session). The reviewer submits structured findings; the issuer computes the verdict. critical/high are always mandatory, low/info never; optional findings never cause another round.
6. **Failure policy** (verification round F5): back-off with jitter per failure fingerprint; the 2nd identical failure escalates the implementer to Opus once; an exhausted fingerprint after escalation — or ANY task-wide budget (remediation cycles, stage failures, review rounds per epoch; lifetime sessions) — becomes a **technical suspension** (§8), never an owner decision. Only genuine owner-only conditions (authentication, billing safety, tampered requirements, isolation, prohibited action, unresolvable conflict) produce a `genuine_blocker` package.
7. **Completeness** (F4): the plan must cover every acceptance criterion; the implementer's `completed_steps` is a claim checked against the plan's own path expectations; an INDEPENDENT review must report every step and criterion `satisfied` for the exact candidate, else mandatory findings force remediation; the handoff re-checks.

## 4. Context renewal (brief §7)

`renewalDecision` renews at **≥70 %** only when every input is present, fresh (≤5 min), model-matched, CLI-version-matched and consistent (`used ≤ window`, window ≥ 8 000); the ratio is compared **unrounded**. Cumulative tokens, cost and subscription utilization are never used. Otherwise it renews on bounded work units (20 turns / 30 min), labelled `bounded_work_unit_*`, `measured:false`, `utilization:null`. A compaction event forces renewal. **Suitability of the ceilings is a heuristic, not a measurement**: 20 turns stay under 70 % of a 200 k window only if average growth is ≤ 7 000 tokens/turn (≤ 35 000 for a 1 M window); no live telemetry was available to validate this (gate G-LIVE-ADAPTER).

Sequence (tested, with SIGKILL at each boundary): boundary → worktree snapshot (untrusted-input validated) → task enters `context_recovery/CONTEXT_RENEWAL` → checkpoint recorded → **verified** → graceful stop → **verified stop** → fresh lease and fresh context id → restore + verify head/snapshot → resume → continue. The prompt takes requirements, scope, acceptance, plan and remaining work **verbatim from the ledger**; model notes are fenced as untrusted data last. A crash at any point is recovered: uncommitted scoped work of a dead session is preserved as a verified `CRASH_RECOVERY` checkpoint before the tree is reset.

## 5. Recovery

Controller start: single-controller OS lock (stale lock from a dead pid is broken, a live one refuses), uncertain intents, un-acked outbox, clock-jump record, then `reconcileSlot` regardless of lease expiry. `reconcileSlot` uses D3.3 `recoveryDecision` (unknown liveness or PID reuse ⇒ investigate, slot stays held), then **guest cleanup (kill + verify)** before `supersedeLease` (token +1) and before any new lease. Unrelated processes are never touched. Stage handlers resume from durable facts (saved plan, pending candidate, recorded test run, submitted review, persisted stage deliverable) instead of repeating paid work. A REVIEW session's finished deliverable is now persisted **before** teardown (F6, §8); the planning/implementing deliverables always were. Recovery preserves the dead session's uncommitted work **atomically with the lease supersession** (§8, F2). After a recovery the token has advanced, so earlier approvals no longer verify (D3.2 binds evidence to the token); `handoff` therefore **re-attests**: each issuer re-issues the same verdict under the new epoch after re-checking the ledger and its own candidate derivation. A *changed* candidate is never re-attested.

## 6. Trust boundaries (what protects what)

| Boundary | Enforced by | Residual |
|---|---|---|
| Candidate/worker → controller | candidate re-derivation, scope + secrets + customer-agent + migration checks, untrusted snapshot/checkpoint/notes handling, read-only tree digest check | the worker kernel boundary is the D3.3 VM (gates G-WORKER-ACCOUNT, G-FULL-WORKER) |
| Controller → issuer keys | the controller imports only `issuer-client.mjs` (static test); keys live in a directory outside every repository; issuers open the ledger read-only | **same OS account in dev**: separate processes are not credential isolation. Real isolation needs per-role accounts + ACLs (G-ISSUER-ACCOUNTS, plan in `key-custody.aclPlan`) |
| IPC | per-connection challenge + HMAC with a per-role secret; closed request schema; ≤64 KB frames; ≤8 connections | Node cannot read a pipe client's SID: authentication is secret possession |
| Reviewer output → approval | issuer recomputes the verdict, independence, model identity and read-only proof from the ledger | ALL issuers trust controller-written ledger rows for test runs and for review-session facts (read-only proof, model identity, termination, independence): a compromised controller could have a review signed. Gate G-ISSUER-INDEPENDENT-FACTS |
| Money/accounts | `--fallback-model`/API-key/base-URL refusal, extra-usage re-check per stage, no setup-token code | provider eligibility is not established (doc 20) |
| Customer agent | candidate refused if it touches `apps/api/**/agent*`; D3.2 evaluator denies the prohibited actions | heuristic path globs |

## 8. Verification-round remediation (PR #254 independent verification, findings F1–F6)

Each finding was reproduced on the unfixed candidate first (`evidence/d34-verification-round-reproductions-BEFORE-FIX-SIMULATED.txt`), then fixed, then pinned by regression tests (`tests/d34-rem-*.test.mjs`, doc 22). Everything remains **simulated and inactive**.

**F1 — re-admission.** Every unit boundary and every fresh-session renewal runs a fresh admission (`engine.checkAdmission(task, need, { ownLease })`): cancellation, resource pressure, subscription eligibility, authentication, extra-usage freshness, the lifetime session budget. The running session is admitted *against itself* (its own lease is not "an occupied slot"; any other holder is `busy`). Denial ⇒ the stop is verified, a verified checkpoint is kept and the task enters the right waiting/blocked state; renewal asks **after** the old session is verified stopped and **before** a lease is acquired, so a denied renewal buys nothing. Telemetry: every token count must be a non-negative safe integer, the window a positive integer ≥ 8 000, the sum positive and ≤ the window — otherwise it is rejected (never a measured percentage) and the bounded work unit decides. **Hard ceilings** (60 turns / 90 minutes by default) apply to *all* telemetry, valid or not; an invalid turn count or start time counts as exceeded.

**F2 — work preservation.** `preserve.mjs`: on every non-completing exit (quota/resource/auth wait, failure, cancellation) the runner — after the stop is verified — captures the worker's uncommitted scoped work, **partitions** it (credential-shaped names/content, out-of-scope, oversize ⇒ *quarantined*: recorded by path + problem code, never content, never restored; one unsafe file never costs the safe ones) and persists a verified checkpoint. Restoration **never consumes** a checkpoint: the newest verified checkpoint valid for the stage/head/plan is restored every time, so a crash during or after a restore can restore again. If no checkpoint is usable (corrupt/missing) the live worktree is preserved *before* it is reset and the unusable checkpoint is recorded. Recovery captures the dead session's tree **before** `supersedeLease` and commits the checkpoint **inside the same transaction** as the supersession (`alsoOnSuperseded`); a recovery bumps the fencing epoch, so when the worktree itself is gone the last snapshot is *carried forward* into a new checkpoint of the new epoch. Evidence of a dead session must be explicit: a liveness probe that throws/is unknown, or a cleanup / stop / process-verification result that is missing or not exactly `verified: true`, leaves the slot **held** and no new session is admitted. An unprovable termination is **budgeted** (it was an unbounded loop of paid sessions: 198 sessions in 400 ticks).

**F3 — intents.** See §2 "Remote effects". Schema V2 adds `tree_digest`, `lease_id`, `superseded_by`, `supersedes`.

**F3b — evidence presence is not authorization (follow-up verification).** The evidence store deliberately accepts AUTHENTIC non-passing evidence, so the ledger can record a failed test run or a review with open findings. `bindingProblem` (creation, dispatch and retry) checked the evidence *types* and their freshness/bindings but not the *verdicts*, so such evidence could authorize an intent. Reproduced first with authentic signed evidence (`verdict: fail` / `findings_open` / `pass` with an open high finding; creation, dispatch and retry all succeeded), then fixed: **every** cited evidence must satisfy the D3.2 rule `isSatisfying` (imported, not re-implemented) judged from the stored payload as it is at that gate; a failing artifact cited beside passing ones is refused too; an unreadable row or one inconsistent with its payload fails closed (`EVIDENCE.UNREADABLE`); the evaluator's rule that independent and security reviews required together come from distinct reviewer contexts is kept (`INTENT.REVIEW_CONTEXTS_NOT_DISTINCT`). Codes: `INTENT.EVIDENCE_NOT_SATISFYING`. Single-use semantics are unchanged: the check runs before `consumeAll`, inside the same transaction, so a refused creation consumes nothing. Independent re-verification also found (and this round fixed) an older hole in the same function: the action spec was looked up with inherited keys, so an action named `constructor`/`toString`/`__proto__` skipped every check; the lookup is now own-keys only. Informational residual: `usableEvidence` (evidence-store.mjs) reads `evidence_types[...]` without an own-key check; unreachable today (acceptance requires an own-key type and `evidence_type` is immutable) but to be hardened with the D3.6 integration. Tests: `tests/d34-rem-f3b-verdicts.test.mjs`.

**Trusted evaluator and reconciliation source — MANDATORY before D3.6 (gate G-INTENT-EVALUATOR).** The durable intent mechanism is a *crash-safety and single-use* mechanism. It is **not** a substitute for the deterministic authority evaluator (`authority/evaluator.mjs`, `evaluate()`), and nothing in D3.4 may be read as authorizing an effect. What `bindingProblem` does NOT do, and the evaluator does: (1) re-derive the candidate, changed paths and policy-relevant facts from a trusted source (the intent only compares recorded identifiers to the ledger head); (2) the action's per-action `checks` — `candidate_binding`, `path_validity`, `scope`, `protected_paths`, `migrations`, `customer_agent`, `control_plane_self_change`, `credentials_env`, `spend`, `launch_environment`, `environment_isolation`, `resource_ownership`, `credential_scope`, `promotion`; (3) that the *requesting identity* is one the action permits; (4) full evidence re-validation (signature against the ACTIVE key set and key validity window at the time of use, issuer permission, bindings to the repository/base/tree/patch/environment/authority digest; independence-of-author and nonce reuse are acceptance-time only) — the intent layer relies on acceptance-time verification plus expiry, policy-revision, fencing, head and satisfaction checks; (5) the **extra evidence the checks add** (`protected_paths`, `control_plane_self_change` and `migrations` add independent + security review; `customer_agent` adds security review; `credential_scope` adds the scope's evidence) — the intent layer uses only the action's listed `required_evidence`, so its distinct-review-context rule also applies only to listed requirements; (6) the evaluator's top-level denials — `ENV.BYPASS_OUTSIDE_ISOLATION`, `FACTS.INCOMPLETE`, `FACTS.ORIGIN_UNVERIFIED`, `PATH.SPECIAL_FILE_MODE`, the claim checks (`TASK.MISMATCH`, `IDENTITY.CLAIM_MISMATCH`, `POLICY.CLAIMED_REVISION_REJECTED`, `CANDIDATE.CLAIM_MISMATCH`), loaded-policy validation (the intent layer checks only that a contract exists and the revision matches) and request/params shape (intent params are only digested). **D3.6 MUST** call `evaluate()` with controller-derived trusted facts and refuse unless it allows, *in addition to* the intent layer, which is the second, durable gate and never the first. Mechanics matter, because a literal call at dispatch denies by construction: `evaluate()` requires an `EvidenceLedger`-conforming ledger whenever a required type is single-use (`LEDGER.REQUIRED`) and rejects an already-consumed single-use id (`EVIDENCE.REPLAYED`), while by dispatch/retry `beginIntent` has consumed that evidence. So (i) `evaluate()` runs at CREATION, before `consumeAll`, inside the same transaction as the intent insert; (ii) D3.6 supplies an `EvidenceLedger`-conforming adapter over the durable store (`nonceStatus` from `evidence_nonces`; `isConsumed` false for ids whose `consumed_by` is this intent's own consumer key) and re-runs `evaluate()` against it at dispatch and retry; (iii) that adapter and the call sites are part of the reviewed integration under G-INTENT-EVALUATOR. Likewise reconciliation: `reconcileIntent` validates the *shape and subject* of an observation but cannot establish that it is true — the caller supplies it. A real effect additionally requires an **authenticated reconciliation source**, enforced by `reconcileIntent` itself: today `authoritative: true` and `observed_at` are caller-asserted and a caller-supplied `authoritative` flag is never sufficient. The observation must either be signed by a policy-pinned reconciliation-reader identity and verified like evidence (key window, nonce, bound to repository + ref + `candidate_sha` + `params_digest`), or be produced in-process by an authenticated remote read whose result is not caller-supplied; `observed_at` comes from the reader; an `absent` observation needs a read made after the dispatch time and consistent with it (not a possibly stale listing); the reader is independently reviewed. Until both exist an `uncertain` intent stays `uncertain`. D3.4 provides neither (the only reader is the simulator); gate **G-INTENT-EVALUATOR** is open.

**F4 — completeness.** Plans carry `covers` (acceptance-criterion indexes) and optional `touches` (path globs). `implementing` applies claims only when the controller-derived changed paths meet `touches`; unfinished steps return the task to implementation (fingerprinted, budgeted, escalating) **before** anything is tested or approved. The independent reviewer must report `coverage` for every step and criterion; anything not `satisfied` becomes a **mandatory finding** (so the issuer's verdict fails). `finalizeReview` and `handoff` both re-check `completenessProblems()` against the stored coverage of the exact candidate. The handoff package records the completeness basis.

**F5 — autonomy when retries run out.** `suspension.mjs`. The task keeps its lifecycle state; a ledger `suspensions` row means *do not schedule until retry_at* (cool-down 30 min / 2 h / 5 h — all below the 6 h extra-usage fact lifetime so a resume never needs the owner to re-verify billing; a test pins this) or *never again by itself* (terminal, after `maxEpochs` = 3 cool-downs or when the session budget of 150 (per generation) is spent). Each suspension starts an **epoch**: per-fingerprint budgets reset, strategy escalates (epoch 1 stronger model; epoch ≥ 2 "choose a materially different approach"), and ONE deduplicated `technical_suspension` notification carries diagnostics (stage, cause, fingerprints with attempts, recent failures, open findings, sessions used, the automatic resume time) and states `owner_permission_required: false`. Budgets are counted **across fingerprints, candidate changes and stages** of the epoch (remediation cycles 6, stage failures 8, review rounds 4 per kind) plus the lifetime session cap — the unfixed code let 202 differently-failing test runs buy 202 implementer sessions. Every retry path has a persisted schedule: stage back-off rows, waits, suspensions, and now the **handoff** (it returned without scheduling anything) and **pending outbox retries** (not in `nextWakeup`). `applyWait` refuses to label a mislabelled blocker: a "blocked" request with no owner-only cause becomes a technical suspension. The lifecycle reducer is untouched; proposal **P5** (21) adds the matching lifecycle state.

**F6 — review deliverable.** The runner persists a finished reviewer deliverable (`review_deliverables`) **before** teardown, tagged with review, execution, context, candidate and tree. It is untrusted until `consumeDeliverable` verifies: the execution is `terminated_verified` (or `abandoned` by a recovery that verified cleanup); the deliverable binds to this review/execution/context and the current candidate + tree; the context is independent of every implementer and other reviewer; and the read-only tree check is recomputed *now*. Mismatch ⇒ discarded (recorded) and a fresh review is bought; unproven termination ⇒ nothing is accepted yet. The issuer independently refuses any review that is not `submitted`, read-only-verified and stopped. SIGKILL tests cover deliverable-persisted, terminated, lease-closed, read-only-verified and submitted boundaries for both reviewers: executions per role equal an uncrashed run.

**Review round 2 (independent Sonnet code review of the first remediation commit; all reproduced, all fixed, tests `d34-rem-round2`).** (1) A checkpoint is a snapshot of uncommitted work ON a worker head: it is restored only if its `worker_head_sha` equals the worker's CURRENT head (the ledger head moves only when a candidate is recorded), otherwise it is *superseded by the worker's commit*; recovery's carry-forward additionally needs the adapter to say the worktree is **missing** (`git.worktreeState`), not merely clean. (2) A capture that FAILED or could not fit the work (oversize / too many files — legitimate work, not "unsafe") never becomes a checkpoint, never supersedes a good older one, fails the renewal before anything is torn down, and a stage start **refuses to reset** a worktree whose work it cannot preserve (budgeted failure → technical suspension, worktree untouched). (3) Suspension notifications and the session budget are per **generation**: `resumeSuspended` starts a new one, so a second terminal disposition is announced again and the explicit resume really grants a fresh session budget. (4) A cool-down is clamped to the remaining freshness of the extra-usage fact (10-minute floor; an already-stale fact is not made worse). (5) A task whose dependency was cancelled becomes an explicit `UNRESOLVABLE_REQUIREMENT_CONFLICT` owner conflict with one package (it used to stall silently). (6) The adapter's turn count can only raise the stream's own assistant-message count; read-only reviewers never preserve files; the failure path honours a spent task-wide budget before escalating; duplicate evidence ids in an intent are one authorization.

**Review round 3 (independent OPUS security review of the delta since the previous security review; findings reproduced, fixed and tested in `d34-rem-round3`; two of the fixes needed correcting — see round 4).** (1) A billing/auth/permission violation (an API-key auth source, extra-usage signal, a non-`dontAsk` permission mode) is classified by the governor **before** any other session complaint and is an owner blocker at the FIRST sighting: `failStage` and `suspendTechnically` route every owner-class code to a genuine blocker with no back-off, retry or cool-down (the first remediation commit had turned it into a 12-session technical retry loop). (2) The read-only proof now also requires a clean worktree (tracked and untracked) after a review; residue whose last writer was a reviewer is never preserved or restored into a writer session (the adapter contract: `treeDigestAfterReview` + `captureSnapshot` must cover untracked files). (3) An approval is issued only while the LEDGER's own review/run time is at most 24 h old, in EVERY recovery epoch (`ISSUER.REATTESTATION_BOUND_EXCEEDED`; a new epoch cannot restart the clock), and an expired one is re-issued at most 6 times — so TTL still bounds how stale a verdict can look. (4) `cov-*` finding ids are reserved to the controller; the **issuer** derives the independent verdict from the coverage table; a completeness-gate refusal withdraws the approval just accepted. (5) The EFFECT of an intent is unique: dispatch/retry refuse a second in-flight or already-achieved effect (`INTENT.EFFECT_NOT_UNIQUE`, plus a partial UNIQUE index), and a proven-absent sibling must be superseded explicitly. (6) Schema V1 is restored byte-for-byte; the findings CHECK is widened by a V2 rebuild. (7) Failure text from adapters is reduced to code-shaped strings (anything credential-shaped or free text becomes `REDACTED:<hash>`) before it reaches history, budgets or notifications. (8) `checkInvocationSafety` parses every occurrence of `--permission-mode` and `--setting-sources` in both `flag v` and `flag=v` forms. (9) `engine.applyWait` never hops a `blocked` task into a waiting state (the exit is `ownerResolve` only).

**Review round 4 (the Opus re-verification of round 3 found two flaws IN the round-3 fixes; both reproduced, fixed, tested as R4-1..R4-4).** Redaction used to run before classification, so a hostile free-text tail turned an owner condition back into a technical one and the owner-branch `stage_failure` row lacked a fingerprint, which made a later suspension throw out of `tick()` (a controller crash loop): `safeCode` now keeps the code-shaped head (`AUTH.…:REDACTED:<hash>`), the owner row carries a fingerprint, diagnostics tolerate absent fields. The re-attestation bound is measured from the ledger's review/run time in every epoch; `executions.end_reason` is code-shaped; a failing dirty-worktree probe is a budgeted failure (it stalled silently); a completeness-gate refusal withdraws the approval in the same transaction as the verdict. Accepted/noted: V2 is FROZEN from here (further schema changes go in V3); findings migrated from a 2acccc07 ledger keep their old `remediated` status (the V1 semantics) — acceptable because no such ledger exists outside tests.

**Issuer change (trusted code, reviewed by the second Opus security pass and re-verified in rounds 3-4, 2026-11-26):** an approval that has **expired** is re-issued under a successor subject (`#r1`, `#r2`…) after the issuer re-derives every fact, within the bounds above; an unexpired approval is returned unchanged. This makes "expired approvals at handoff" recoverable without an owner and without a lifecycle back-edge **only while the review/run is at most 24 h old**; beyond that the task is terminally suspended AT ONCE with cause `HANDOFF_APPROVALS_TOO_OLD` (diagnostics carry the issuer code; the notification says a new test run and new reviews are required — a manual dead end until proposal P3(c), `publishing → testing`). The same bound applies to a FIRST issuance: a review opened more than 24 h before it is submitted is refused and a fresh, budgeted review is bought (fail-closed). A hostile worker can force an owner blocker by emitting a failure text that starts with an owner-class code: an interruption, never a bypass.
