## 4. Recorded for the integration by the independent-verification remediation (nothing here is closed)
1. **Staging dispatch head-binding gap (R-25, doc 40 §5; control plane; needs the protected workflow).** `staging-candidate.yml` `workflow_dispatch` takes only `pr_number` — there is NO SHA input — so V3 cannot bind a dispatch to the candidate head it intended. If the PR head moves between V3's decision and the run, the run verifies the NEW head. V3 contains this on the READ side: only staging runs whose `head_sha` equals the candidate AND whose PR is this task's PR count (a run for any other head is not applicable and never masks), the verifier re-checks the PR head when it issues `staging_gate` and `delivery_verification`, and a head change invalidates every milestone. What remains is a protected change: an optional `head_sha` input on the dispatch that the workflow compares with the PR head before any staging work, with the same refusal the `workflow_run` path has. Add it to the P2 control-plane PR (it is a workflow edit; the V2 guard re-pin applies) or record the decision to live with read-side containment. Until then the activation gate for staging dispatch (`dispatch_staging_candidate`) must stay inactive.
2. **Live controller exclusion (R-32, prerequisite for any live controller).** The delivery controller does not itself take the D3.4 single-controller OS lock; on start it ends the previous process's in-flight effect rows (`process_ended`) so absence can be decided. A SECOND live controller on the same ledger would end the first one's live effect rows and let absence be concluded while its request may still land. A live controller MUST take the single-controller lock before `start()`, with proof the previous holder is gone (G-LIVE-RECOVERY-ADAPTERS). The remote-side compare-and-swap (fast-forward-only push, one open PR per head, run-attempt check) is a backstop, not a substitute.
3. **Do not treat the lifecycle state as eligibility.** Under the authoritative lifecycle (without P6v3) a withdrawn task still reads `merge_eligible`. D3.7 and any consumer MUST call `controller.currentEligibility(task)` / `deliveryEligibility` (doc 34 §5) and never act on the state name or on an unexpired package signature.
4. **Reader contract for partial re-runs.** `checkState` carries an earlier-attempt success only for a completed successful latest attempt. The live reader must confirm what GitHub reports for jobs that were not re-run (which attempt, which run) before activation (G-REMOTE-READER); the simulator models both the full re-run and the carry-over.
5. **Ledger schema V4** changed inside this unmerged PR (`delivery_milestones_reached_at` / `al_milestone_reached_again`): no deployed ledger exists, so there is no migration.
