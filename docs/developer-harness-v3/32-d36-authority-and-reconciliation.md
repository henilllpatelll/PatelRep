# Developer Harness V3 — 32 D3.6 authority at every effect boundary, and authenticated reconciliation

**Status: implemented, SIMULATED and INACTIVE.** The authoritative policy activates nothing, so every real delivery effect is refused; the full path is demonstrated only in the labelled `PROPOSAL_UNDER_TEST` configuration (doc 39) with test keys and temp ledgers.

## 1. The evaluator before every effect (closes the design of G-INTENT-EVALUATOR; the gate stays OPEN)
`delivery/authorize.mjs`. The D3.2 evaluator (`authority/evaluator.mjs`) is **unchanged and is the decision**; the intent layer is the second, durable gate.
* **Trusted facts** are re-derived by the controller for every evaluation: candidate facts from the trusted fact source (D3.2 shape: changes, modes, base migrations, added lines, origin), the task's fencing token / revision / authority (`authorityOf`), the worker environment record, the current main tip from a verified observation, and (for P7) the trusted delivery record. The identity is fixed per action (`ACTION_IDENTITY`); a requester can only *claim* one, which is checked.
* **Creation:** `evaluate()` runs inside the SAME transaction as the intent insert, BEFORE any consumption. Only on `allow` is anything consumed — exactly the evaluator's `consumes` (its accepted single-use evidence). Multi-use approvals are CITED (re-validated at every gate) and not consumed. A refusal leaves nothing behind (rolled back). The intent stores the exact effect parameters (`params_json`, bound by `params_digest`) and the authorized request digest.
* **Dispatch and retry:** `reauthorize()` re-derives the facts, re-runs `evaluate()` against the CURRENT policy and requires `allow`, an identical request digest, no new consumption, and the exact parameters still matching the trusted delivery facts (`validateParams`: task-owned branch, owned PR/run, current head, remote ref unchanged since authorization); then the intent layer's `markDispatched` re-validates its own bindings, in the same transaction.
* **Consumed-evidence semantics (reconciled with doc 30 §1):** the storage form is `consumed_by = intent:<idempotency_key>`. `DurableEvidenceView` (an `EvidenceLedger` over the durable store) reports evidence consumed by THIS consumer as *held* and evidence consumed by anything else as consumed (`EVIDENCE.REPLAYED`); an unknown id is consumed (fail closed). Consumption is never undone: a single-use artifact authorizes only the intent that consumed it.
* **Strengthening only:** the delivery path additionally requires `independent_review` for publication and a PR, and `security_review` whenever the task's risk class requires it — under the authoritative evaluator in the delivery layer, under P7 inside the evaluator.

## 2. Outcomes
`recordOutcome`: success ⇒ `succeeded`. A failure is `failed` (retryable) ONLY with a verified, intent-bound observation of a rejection BEFORE any effect; every other failure — timeout, lost response, reset, exception, unclassified status, abort — is `uncertain`. D3.4 treated a reported failure as retryable; that was the weakness the brief names, and it is removed (tests updated, doc 40 §3).

## 3. Authenticated remote observations (`delivery/observation.mjs`)
* Signed with Ed25519 by a key the ACTIVE policy pins for `delivery_verifier` (the trusted reader, which reads the remote with its own access), under the domain `patelrep-developer-harness-v3-remote-observation\n` (an observation can never be replayed as evidence, or evidence as an observation); fresh (≤10 min, ≤60 s future skew); bound to repository, task, intent, `params_digest`, candidate and policy revision; a closed schema.
* `reconcileIntent` accepts only objects produced by `verifyRemoteObservation` in this process (a module-private brand). A copied object with `authoritative: true` is `OBSERVATION.UNAUTHENTICATED`. A read made before the dispatch is refused.
* **present** reconciles at once (`reconciled_succeeded`) and wins forever. **conflict** (the remote shows neither the effect nor its absence: a foreign PR, a different head) stays uncertain and becomes ONE owner decision. **absent** is concluded only when `absenceProven()` holds over the DURABLY recorded reads (`remote_observations`): ≥2 distinct reads, each ≥60 s after the dispatch, ≥30 s apart, and no present ever seen. A single lookup is never proof (eventual consistency is tested with a read lag).
* After a controller restart, `markDispatchedAsUncertain`; after a ledger restore, the D3.5 seal — every unfinished intent is uncertain; only these reads settle it. A retry happens only after proven absence, under re-validated authorization; if that authorization expired, a NEW intent with fresh evidence supersedes it.
* **What it does NOT prove:** that the reader is honest. The reader is the simulator here; a live reader with its own read-only credential and OS account is gate **G-REMOTE-READER**.

## 4. Remediation F2 (independent verification): remote outcomes and the reconciliation boundary
* **A response is success only with ACTION-SPECIFIC positive confirmation** (`delivery/effect-subjects.mjs` `confirmResponse`): the push must name the exact branch and sha, an update / ready the exact PR number, a re-run the exact run and `attempt + 1`, a staging dispatch `accepted: true`, a PR creation a positive number (the number itself is only ever learned from the authenticated observation). An empty object, an array, a string, `{ ok: true }`, an explicit error, or a response about ANOTHER object is **uncertain** (`PUBLISHER.UNCONFIRMED_RESPONSE` / `WRONG_REMOTE_OBJECT` / `UNRECOGNIZED_RESPONSE`) and is reconciled independently. Before the fix `{}` for a push that never reached the remote was recorded as `succeeded` (evidence file `d36-remediation-reproductions-BEFORE-FIX-SIMULATED.txt`).
* **Absence needs reads taken AFTER the end of the request.** The settle window now starts at the later of the dispatch and the end of the effect's own request in ANY of its end states: `settled` (ordinary), `settled_late`, `process_ended` (the previous controller process was verified gone). Before the fix `settled` was missing from that query, so two absent reads taken while a request was still in flight — then an uncertain ordinary failure — concluded absence at once. The rule itself is unchanged (settle 60 s, at least 2 DISTINCT reads, at least 30 s apart, no `present` ever). **The end of a client never proves the server-side operation cannot still complete**: it only starts the window; a request that never ends keeps the intent uncertain (`EFFECT_STILL_IN_FLIGHT`) and, after `unresolvedEffectAfterMs` (6 h), the effect is RETAINED explicitly — a durable `unresolved_effect:<intent>` record, one `effect_unresolved` outbox notification, never retried, still blocking the task and the staging hold. The remote-side compare-and-swap (push `expected_old`, one open PR per head, run-attempt check) remains the backstop against a delayed original landing after a retry; it is exercised in the simulator (`delay_effect` fault) and is the property a live adapter must keep.
* **The reconciliation boundary binds the observation to everything it is about** (`ledger/intents.mjs` `observationProblems`): repository (the task's), the EXACT effect subject derived from the recorded parameters (`effectSubject`; a delivery effect whose object cannot be named is never reconciled), task, intent, parameter digest, candidate, the ACTIVE policy revision (`reconcileIntent` now REQUIRES `policy`: `OBSERVATION.ACTIVE_POLICY_REQUIRED`), freshness (10 min, enforced at the ledger as well as when the envelope was verified), a read made after the dispatch, and **replay** (an observation id counts once: `OBSERVATION.REPLAYED`). The controller also passes repository and subject to `verifyRemoteObservation`.
* The watchdog's START record (`operation_deadlines`) is no longer best effort: if it cannot be written the request is never sent. Settlement bookkeeping stays best effort because a row left `running` is only ever read as "still in flight" (fail closed).
